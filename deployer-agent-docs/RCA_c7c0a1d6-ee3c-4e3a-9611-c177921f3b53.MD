# RCA — 520 en aptiva-rl.cl / aptiva-db (run c7c0a1d6-ee3c-4e3a-9611-c177921f3b53)

## Resumen ejecutivo
El deploy **compiló y se promovió con éxito** (health check verde a las 13:46 UTC), pero el pod de origen (Next.js standalone, puerto 3000) **deja de responder HTTP poco después** (~13:47). No es un crash ni un fallo de build: el proceso `node server.js` arranca, imprime "Ready", **no reinicia (restart_count=0), no hay OOM, no hay CrashLoop**. El problema es un **cuelgue en el manejo de requests**: el puerto acepta la conexión TCP pero **el handler nunca devuelve headers**. Eso hace fallar la readiness probe sobre `/`, K8s saca los pods de los endpoints del Service, y Cloudflare —sin origen sano— devuelve **Error 520** en TODAS las rutas.

## Evidencia observada en producción
- **Estado del pod**: 2 réplicas `Running`, `restart_count=0`, sin `OOMKilled`, sin `CrashLoopBackOff`, sin terminaciones.
- **Eventos K8s (kill_findings)**:
  - `Startup probe failed: Get "http://10.116.80.218:3000/": context deadline exceeded (Client.Timeout exceeded while awaiting headers)` → **el puerto conecta pero el handler no responde** (cuelgue).
  - `Startup probe failed: ... connection refused` (segunda réplica, ventana de arranque temprana).
- **Logs de runtime**: solo líneas de arranque (`▲ Next.js 15.5.18`, `✓ Ready`). **0 líneas de error / stacktrace / DB / timeout / rejection.** Es un cuelgue silencioso, no una excepción.
- **Build**: `build_state: SUCCESS`. `jspdf` se instaló con `yarn --frozen-lockfile` sin errores de dependencias nativas (canvas). El único error de build (`restore-pip-cache: No URLs matched`) es benigno y no aplica a Next.js.
- **Env vars de producción**: TODAS presentes y no vacías → `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_BASE_URL`, `STORAGE_BUCKET`, `CORS_ORIGINS`, `JWT_SECRET`. (NOTA: no se pueden ver los *valores*, solo su presencia/no-vacío. También existen `MONGO_URL`/`DB_NAME` heredados del template, la app usa Supabase Postgres.)
- **Health check en vivo del origen** (`https://aptiva-db.emergent.host`, sin pasar por el dominio custom): **520 en `/`, `/api/`, `/_next/static/` y `/favicon.ico`**, con respuestas rápidas (82–278 ms). El 520 rápido incluso en assets estáticos = el Service no tiene endpoints "ready" (los pods cayeron de la readiness), síntoma aguas abajo del cuelgue del handler.

## Causa raíz (diagnosticada, NO reproducida)
Un **bloqueo síncrono/await que nunca resuelve durante el server-side de Next.js**, en una ruta que la app ejecuta en cada request (muy probablemente el **root layout** o la **página `/`**, ya que afecta a TODAS las rutas incluyendo la probe sobre `/`). Como funciona en preview (localhost) y falla en prod con las mismas env vars presentes, la diferencia está en **conectividad/valor de un recurso externo en el entorno de producción**. Candidatos, por probabilidad:

1. **Consulta a Supabase Postgres colgada en request-time** (más probable). Código server-side (layout/page/API) hace una query vía `DATABASE_URL` (pooler IPv4, puerto 6543 = modo *transaction*/PgBouncer) **sin connect timeout ni statement timeout**. Si el clúster de producción no alcanza el pooler (egress de red / IP allowlist de Supabase / IPv4 vs IPv6 / pooler saturado), la conexión/consulta **queda colgada indefinidamente** → el render nunca emite headers → readiness falla → 520. Encaja con "arrancó bien y a los ~1 min dejó de responder" (agotamiento/estancamiento de conexiones del pooler bajo el primer tráfico).
2. **Self-fetch server-side a `NEXT_PUBLIC_BASE_URL`** durante SSR del layout/página. Si en prod `NEXT_PUBLIC_BASE_URL` apunta al propio dominio (aptiva-rl.cl) y el layout/page hace `fetch()` a esa URL durante el render, se produce un **deadlock circular** (el dominio está caído porque el SSR espera al dominio). En preview no ocurre porque apunta a localhost.

## Qué revisar / acciones para levantarlo (E1 / usuario)
1. **Localizar el bloqueo en el render raíz**: revisar `app/layout.js` y `app/page.js` (y cualquier `instrumentation.ts`) por llamadas server-side a DB o `fetch()` que se ejecuten en cada request. Mover el fetch de datos a client-side o a handlers con manejo de error/timeout; el root layout NO debe hacer llamadas de red bloqueantes sin timeout.
2. **Endurecer la conexión a Postgres**: añadir `connectTimeout`/`statement_timeout`/`query_timeout` al cliente PG y capturar errores (para que falle rápido y loguee en vez de colgar). Confirmar que se usa el **pooler transaction (6543)** correctamente (p. ej. `pgbouncer=true`, sin prepared statements incompatibles) y que las conexiones se liberan.
3. **Verificar el VALOR de `DATABASE_URL` en prod** (host del pooler IPv4 correcto, puerto 6543, credenciales) y que el clúster `target-8` tiene **egress permitido** hacia el pooler de Supabase (allowlist de red de Supabase). El agente/deployer solo puede confirmar que la clave existe y no está vacía, no su valor.
4. **Verificar el VALOR de `NEXT_PUBLIC_BASE_URL`** en prod: no debe provocar self-fetch server-side al propio dominio.
5. Tras corregir el código y/o los valores de secretos: **redeploy**. (Editar valores de secretos existentes se hace en UI → pestaña Secrets; añadir claves nuevas = agregarlas al `.env` de preview y redeploy.)

## Descartado explícitamente
- Fallo de build / dependencia faltante (jspdf/canvas) → build SUCCESS, deps instaladas.
- Env var faltante o vacía → todas presentes y no vacías.
- OOM / límite de tier → sin OOMKilled, sin reinicios.
- Crash / CrashLoopBackOff / puerto mal bindeado → el proceso vive, imprime Ready, conecta TCP en 3000.

## No reproducible en sandbox
El cuelgue depende de la red/DB real de Supabase y de los valores de secretos de producción; el sandbox eph no recibe secretos ni tiene acceso a Supabase, por lo que **no se puede reproducir ahí**. Además el sandbox no pudo levantarse (`eph_source_check_failed`, error interno). Diagnóstico basado en eventos de pod, logs de runtime, estado de build/secrets y sondeos HTTP del origen.
